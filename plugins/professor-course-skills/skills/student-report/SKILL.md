> **Non-negotiables.** This skill proposes; a person decides.
>
> - Write to `work/<RUN_ID>/`, never into `courses/`. Draft identifiers carry a
>   `-DRAFT-` segment so they cannot be mistaken for records.
> - **Claims come from the professor.** Never invent a learning outcome, a
>   rubric criterion or an assessment weight — write `TODO` and say what is
>   missing. Artefacts that serve an existing claim you may draft; that is the
>   job. Concepts and modules may be **proposed** from source material the
>   professor supplied, with `extensions.proposal.source` naming where each came
>   from — proposed, not invented, and inert until approved.
> - **Never run `ainar approve`,** and never `ainar lms push --target canvas-api`
>   or `--target sheets-api`. Approving your own suggestion, or posting a grade a
>   student can see, is the one place a human enters. Show the command instead.
> - **No student name, email or institutional number in any file,** including a
>   grading comment or a lesson brief. Write the identifier.
> - Before reporting anything: `bin/ainar validate <COURSE> --drafts
>   work/<RUN_ID>`, and fix every error.
> - Never recompute by hand what a command does exactly — `score-items`,
>   `gradebook`, `extract-evidence`, `roll-up`, `calibration`, `lms plan`.

# Report on one student

**Needs:** a course in YAML and recorded evidence. Partial without the CLI.

This is the most consequential thing in the workspace. A report about a real
person, written by an agent, read by someone with power over their degree. Two
rules follow from that, and everything else is detail:

**Say only what the evidence says.** Every claim traces to a record.

**Never write it into the repository.** It names a student.

## 1. Get the record

```bash
bin/ainar student STUDENT-JNG7SN --course-version CSS-4008-2026-FALL --json
```

That returns, from recorded evidence only: outcome-level proportions with the
sources behind them, concept-level results, capability levels with a source
count, gaps with the prerequisite state of each, and open signals.

Read `gaps[].prerequisite_state` carefully. It distinguishes `needs_review`
from `no evidence`, and those mean opposite things — see below.

## 2. Write it

Default location, outside the workspace:

```
~/.ainar/reports/CSS-4008-2026-FALL/STUDENT-JNG7SN.md
```

Ask the user if they want it somewhere else. Never `courses/`, never `work/`,
never `dist/`. If you are unsure whether a path is inside the workspace, it is.

`templates/` beside this skill holds two shapes, and which one you use is the
question §3 asks: `for-the-professor.md` and `for-the-student.md` are different
documents with different registers, not one document with the names changed. Read
`templates.yaml`, ask which it is, and use that one. `references/templates.md`
has the convention.

Structure — this is `for-the-professor.md`:

```markdown
# STUDENT-JNG7SN — CSS-4008 2026-FALL
Draft, from recorded evidence as of 2026-11-08. Not a grade.

## Demonstrated
- **LO-01 Explain core AI problem types** — 83% across 5 pieces of evidence
  (SUB-9060, RESP-9060-0101). Consistent across a quiz and a written answer.

## Not yet demonstrated
- **LO-02** — no evidence recorded. Nothing has assessed it yet; this is not a
  finding about the student.

## Where it is breaking down
- **Model evaluation** (0%, 2 pieces of evidence). It depends on train-test
  separation, which is itself `needs_review` (EVID-2801). Working forward from
  evaluation metrics is unlikely to hold until the split is secure.

## Suggested next step
- ...

## Behind this report
Evidence: EVID-2801, EVID-9060-0102-1, …
Generated by student-report-skill from records approved by USER-ARD-A01.
```

Include the evidence identifiers. A report a professor cannot check is a report
they have to take on faith, and they should not have to.

## 3. If it is going to the student

Say so and change the register. A report *about* a student, for a professor, can
say "not yet demonstrated". A report *for* a student needs to say what to do
next and must not read as a verdict. Ask which it is before writing; do not
guess.

Either way the professor reads it before the student does. Say that in your
hand-over.

## Without the CLI

Read `records/` and `samples/`, filtered to that one identifier,
instead of `ainar student`.

One distinction becomes harder and matters more. With the package, a blank
means **the student was never assessed on that concept**. Without it, a blank
may mean that *or* that the evidence chain was never run — nobody executed
`ainar extract-evidence`, so decisions exist but evidence does not. Those are
different facts about the course and you must not merge them. Say which one you
are looking at, and if you cannot tell, say that.

Never read a blank as a low score, in either case.

The report still goes **outside** the repository, because it names a person.

`references/working-without-the-cli.md` carries the file layout, the identifier patterns, the read-based checks and how approval works by hand. Read it before starting.

## Rules

- **Absence of evidence is not evidence of absence.** A concept with no
  evidence was never assessed. Say "nothing has assessed this yet", never
  "the student has not learned this". The `student` command repeats this at
  the bottom of its own output for the same reason.
- **No claim without a record behind it.** If you want to write "struggles with
  abstraction" and no evidence says that, do not write it.
- **Never predict.** No grade forecasts, no "likely to fail", no ranking
  against classmates. The model records what happened.
- **A single data point is a single data point.** One wrong multiple-choice
  answer is not a finding. Say how much evidence stands behind each claim, and
  let three pieces read differently from one.
- **No personality, no effort, no motivation.** You have evidence about
  artifacts, not about a person. "The report did not justify the method" is
  supportable; "the student was careless" is not.
- **Explain a gap through its prerequisites.** That is what makes a report
  actionable rather than merely accurate.
- **Never resolve the name into the repository.** `ainar student --with-names`
  refuses to write inside the workspace, and so should you.
- **The professor decides what reaches the student.** You draft; they send.
